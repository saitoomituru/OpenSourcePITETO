## 1. 対象・範囲・除外

このノートは、ソフトウェア工学におけるデプロイ、保守、脆性、脅威モデル、再現コストを、家庭でポテトチップスを作って食べる工程へ言い換える哲学思考実験である。

対象は次の三者を同じ依存関係図へ戻すことにある。

1. ソフトウェアを設計、試験、配備、保守するOSSエンジニア
2. 芋を調達、保存、検品、調理、片付けする家庭内作業者
3. 成果物を利用し、身体と味覚で最終結果を観測する利用者

家庭内作業者の典型例として「ママ」という語を使う場合があるが、性別役割を固定する意図はない。実際の作業者は母、父、祖父母、子、同居人、単身者、地域共同体、調理担当者など誰でもよい。

このノートは、家庭料理を商用食品安全保証へ昇格させない。個別の芋の毒性、安全性、疾病、法的責任を断定する資料でもない。危険兆候がある入力物を、思考実験や再現性のために食べることを求めない。

## 4. 材料・設備・環境

この思考実験の最小環境は次である。

- 芋、油、調味料、熱源、調理器具
- 芋を観察し、調理し、食べて判断できる人間
- GitHub、Codespaces、ローカルエディタ等のいずれか
- 自然言語をMarkdown、diff、commit、Issueへ構造化できるコーディングAI環境

重要なのは、高価な設備ではなく、物理結果と文書履歴の両方を閉じることである。

```text
物理側: 芋 -> 保存 -> 検品 -> 加工 -> 加熱 -> 冷却 -> 試食 -> 片付け
文書側: 条件 -> 観測 -> 差分 -> note -> diff -> commit -> issue -> 次の追試
```

## 5. 手順と変更差分

1. ソフトウェア工学上の概念を一つ選ぶ。
2. 対応するポテト工程を見つける。
3. 両者で失われがちな人間労力を列挙する。
4. 攻撃者がいなくても壊れる状態遷移を列挙する。
5. 「誰が悪いか」ではなく、どの前提がいつ崩れたかを記録する。
6. 追試可能な観測項目と停止条件へ変換する。
7. 過剰な一般化をせず、Issueへ責務別に接続する。

## 6. `[FACT]` 事実・観測

- ポテトチップスは、レシピ文書をコピーしただけでは物理的に生成されない。
- 調達、保存、検品、調理、試食、清掃には人間の時間、身体、電力、油、水、場所が必要になる。
- 同じレシピでも、品種、畑、収穫、保存、厚さ、器具、温度、湿度、作業者によって結果が変わり得る。
- 芋や油などの入力物は、保存中に状態が変化し得る。
- GitHub上の文書、Issue、commitは、台所の入力物や家庭内作業を自動的には再生産しない。
- コーディングAIは観測を構造化できるが、芋を検品し、揚げ、食べ、片付ける主体ではない。

## 8. `[INTERPRETATION]` 言い換えシート

### 8.1 配備と提供

| ソフトウェア工学 | ポテチ／家庭内兵站 | 見えなくなりやすい労力 |
|---|---|---|
| sourceを公開する | レシピを公開する | 説明、撮影、校正、翻訳、履歴管理 |
| buildする | 芋を切って揚げ、乾燥仕上げする | 材料調達、熱源、身体、待ち時間 |
| deployする | 食卓または袋へ出す | 盛り付け、冷却、配膳、保存判断 |
| release artifact | 食べられるポテトチップス | 失敗ロットの処理、清掃、油の後始末 |
| user acceptance test | 冷却後に食べて評価する | 味覚、身体状態、文化、用途の差 |
| rollback | 加熱停止、廃棄、別用途への切替 | 損失を引き受ける人、再調達 |
| maintenance | README、依存、Issueを保守する | 買い物、保存、器具保守、台所維持 |

### 8.2 環境差

| ソフトウェア側 | 芋側 |
|---|---|
| OS、runtime、CPU、依存版 | 畑、土壌、気候、品種、収穫時期 |
| build flags | スライス厚、前処理、油量 |
| deployment target | 鍋、フライヤー、オーブン、エアフライヤー |
| network／external API | 室温、湿度、換気、電源、家庭設備 |
| operator procedure | 揚げ手、試食者、片付け担当 |
| cached artifact | 保存芋、開封済み油、湿気た完成品 |

同じsourceまたは同じレシピは、同じ入力状態と同じ実行環境を保証しない。

### 8.3 脅威モデル

| 脅威源 | ソフトウェア | ポテト |
|---|---|---|
| 悪意ある攻撃者 | 改ざん、侵入、依存汚染 | 故意の異物混入、表示改ざん |
| 時間経過 | 証明書期限、依存陳腐化、model drift | 発芽、緑化、腐敗、油の酸化、湿気 |
| 正常機能の目的不一致 | 自動更新が互換性を壊す | 芋が発芽し次世代へ資源を回す |
| 環境変化 | API停止、OS更新、回線断 | 気温、湿度、停電、器具差 |
| 観測不足 | test未実施、log欠損 | 保存履歴不明、温度未計測、見落とし |
| 人間資源枯渇 | maintainer burnout | 調理者の疲労、買い物不能、片付け未完 |

ここでの重要点は、悪意がなくても事故が成立することである。

```text
正常だった入力
    ↓ 時間・保存・環境・生物活動
前提条件が変化
    ↓
同じ手順を再実行
    ↓
以前とは異なる結果または停止条件
```

脅威モデルは「悪人一覧」ではなく、資産、状態遷移、前提、停止条件、回復可能性の一覧である。

### 8.4 無償ではない労力

```text
OSSエンジニア
  設計、実装、レビュー、Issue対応、依存更新、説明、撤退判断

家庭内作業者
  調達、保存、検品、調理、配膳、清掃、廃棄、再調達

利用者
  試す、身体で受ける、好みを返す、失敗条件を報告する
```

ソースが無料であることは、保守者の生活費が無料であることを意味しない。

家庭料理が代金なしで提供されたことは、家庭内作業者の時間、身体、知識、電気、油、水、片付けが無価値であることを意味しない。

「ママが作ったから無料」「OSSだから無料」は、価格表示の観測であって、再生産コストがゼロという自然事実ではない。

### 8.5 配備成功の二輪

```text
工学側の成功
  手順が実行され、危険停止を越えず、結果と条件が記録された

生活／需要側の成功
  食べる人にとって受け入れ可能で、また食べたい／作りたい需要がある
```

安全、規格適合、再現可能性だけで「おいしい」「需要がある」とは証明できない。

一方、物語、愛情、家庭の努力、「ママが作った」という価値だけで、腐敗、異臭、発芽、緑化、油煙、アレルギー等の停止条件を解除できない。

### 8.6 家庭内SRE／maintainerという見方

家庭内作業者は、完成品だけを作る人ではない。

- 在庫を監視する
- 入力物の状態を点検する
- 設備の能力差を吸収する
- 異常時に停止する
- 失敗ロットを処理する
- 利用者の好みを聞く
- 次回の工程を更新する
- 片付けて次の稼働可能状態へ戻す

これは小規模なSite Reliability Engineering、サプライチェーン運用、カスタマーサポート、保守を一人または少人数で兼務する状態に近い。

ただし、家庭を企業へ縮約したり、家族関係を雇用契約と同一視したりしない。ここで移植するのは、見えない依存と労力を可視化する定規である。

## 9. `[HYPOTHESIS]` 仮説

### H1: 芋はデプロイリスクの低摩擦教材になる

芋を揚げて食べ、差分を自然言語でAIへ渡すだけで、次を体験できる可能性がある。

- buildとdeployの違い
- artifactと利用結果の違い
- 環境差
- 時間依存脆性
- rollback／abort
- user acceptance
- maintenance cost
- provenance

### H2: 家庭内労力とOSS保守労力は同じ誤認を受ける

両者とも、成果物が手元へ低価格または無償で届くため、供給側の再生産コストが視界から消える。

### H3: 攻撃者なしの脅威モデルが理解しやすくなる

芽、緑化、湿気、酸化、器具劣化は、悪意のない状態遷移として目視しやすい。これにより、脅威モデルを犯罪者探しから前提崩壊の管理へ戻せる可能性がある。

### H4: AIは無償労力を削減できるが消去はできない

AIは次を軽減できる。

- ログ整形
- 比較表
- 翻訳
- Issue草案
- 差分説明
- 未記入項目の検出

しかし、物理調達、検品、調理、試食、清掃、身体リスク、最終責任は残る。AI導入による文書コスト削減を、供給者全体の無償化と誤認しない。

## 11. Issue接続候補

### Issue #2: 品種 × 厚さ

環境差、入力provenance、畑・品種・保存状態を、ソフトウェアのruntime／dependency差として比較する。

### Issue #3: 複数回ログ

調理時間だけでなく、調達、検品、片付け、文書化を含む再生産コストを任意項目として記録する。人間の価値を作業時間へ還元するKPIにはしない。

### Issue #4: Recovery

湿気た完成品だけでなく、時間経過で状態が変わった入力と成果物を区別する。Recovery不能な劣化を、再加熱で帳消しにしない。

### Issue #5: Safety

悪意ある攻撃者なしでも成立する脅威源として、時間、保存、正常な生物活動、設備差、疲労、観測不足を追加検討する。
