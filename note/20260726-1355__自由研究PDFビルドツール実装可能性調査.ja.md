## `[FACT]` 事実・観測

### 現行repositoryのライセンス境界

- ルート[`../LICENSE`](../LICENSE)は`CC-BY-4.0`であり、Apache-2.0ではない
- 現行[`../lib/README.md`](../lib/README.md)は、ルート`LICENSE`が`lib/`のツールにも適用されると記載している
- Creative Commons自身は、CC licenseをcomputer softwareへ推奨していない
- したがって、将来のbuilderコードをApache-2.0にするなら、subdirectory単位の適用範囲、NOTICE、ルート文書からの例外を人間が明示する必要がある
- このノートは「現在のCC-BY-4.0を無効にする」「既存ファイルを再ライセンスできる」とは判断しない

### 候補component

| 責務 | 候補 | upstream表記 | 調査時の位置づけ |
| --- | --- | --- | --- |
| Markdown→HTML | `markdown-it-py` + `mdit-py-plugins` | MIT | Python側の第一候補 |
| LaTeX風数式→static HTML/MathML | KaTeX | MIT | Node側でpre-renderする候補 |
| mindmap→SVG | Mermaid | MIT | `mindmap`対応。headless browser依存を追加調査 |
| HTML/CSS/SVG→PDF | WeasyPrint | BSD-3-Clause | 第一候補。ただしPango等のnative依存あり |
| 日本語text layout | Pango | LGPL-2.1-or-later | WeasyPrintが使うsystem/shared library候補 |
| 2D描画 | Cairo | LGPL-2.1またはMPL-1.1 | native dependency候補 |
| PDF→PNG／metadata検査 | Poppler CLI | GPL | builderへ同梱せず、外部QA command候補 |
| alternative compiler | Typst | Apache-2.0 | PDFは強いがMarkdown変換責務が別途必要 |
| universal converter | Pandoc | GPL-2.0-or-later | core同梱候補から外し、外部adapter候補 |

MIT、BSD、Apache、LGPL、MPL、GPLというラベルだけで最終適合を判定しない。versionをlockした後にdirect／transitive dependencyのlicense text、NOTICE、配布形態、link方法を再監査する。

### フォント

- M PLUSの公式siteは、現行fontをSIL Open Font Licenseで公開し、licenseを保持した利用、改変、再配布、文書埋め込みを案内している
- Notoの公式repositoryはOFL-1.1で、license textはfontの埋め込みを許容し、生成文書へ同じlicenseを要求しないとしている
- IPAexはIPA Font License Agreement v1.0への同意をdownload条件としている
- WeasyPrintはPango／Fontconfigが発見したfontを利用し、PDFへ自動埋め込みし、既定で使用glyphをsubsetする

「Open font」でもlicenseは同一ではない。M PLUS／NotoのOFLとIPA Font Licenseを同じnoticeへ潰さず、fontごとのreceiptを保持する。

## `[RESULT]` 調査結果

実装は可能性が高い。ただし、次の理由でこのturnでは実装しない。

1. 現行repositoryはcontentとtool codeのライセンス境界が未分離
2. Mermaidのserver-side SVG化がheadless Chromiumを要求する構成では、依存容量とthird-party license面が急増する
3. WeasyPrintのnative dependencyと、PDF page render用Popplerがlocal環境にない
4. font取得元、checksum、license receipt、埋め込み確認のcontractが未確定
5. 子ども向け入力を扱うなら、remote fetch、absolute path、SVG、HTML、無制限renderを先に閉じる必要がある

第一候補は「Python orchestrator + static HTML + WeasyPrint」である。Typstは有力な別案だが、Markdown／LaTeX風入力をTypst syntaxへ変換する独自責務が増えるため、現時点では第二候補とする。

## `[INTERPRETATION]` 考察

寺子屋demoの主役はPDF engineではなく、次の履歴が一本につながることである。

```text
観測 → 写真 → 仮説 → Markdown差分 → Review → PDF → 発表後の反例
```

そのため、GUI専用binary formatへ寄せるより、Markdown、Mermaid text、local image path、front matterをGitで比較可能にする価値が高い。一方、小学生へdependency managerやfont license監査を直接背負わせない。保護者／先生用の`bootstrap`と`doctor`、研究者用の`build`を分離すると役割が明確になる。

### 推奨module構成案

```text
lib/report_builder/
  README.md
  LICENSE
  NOTICE
  THIRD_PARTY_NOTICES.md
  pyproject.toml
  uv.lock
  package.json
  package-lock.json
  font-manifest.json
  templates/
  fixtures/
  src/
```

commitするもの:

- source、template、test fixture
- Python／Nodeのmanifestとlockfile
- fontの公式download URL、version、SHA-256、license ID、license URL
- third-party notice生成手順
- bootstrap、doctor、build、verifyのinterface

Gitから除外する候補:

- `.venv/`
- `node_modules/`
- `.cache/piteto-report/`
- downloadしたfont binary
- headless browser binary
- intermediate HTML／SVG
- build output PDF／page PNG

ただし最終PDFを研究成果として公開する場合は、生成物を機械cacheではなくrelease artifactまたは明示的な成果物pathへ昇格できるようにする。

### フォントpipeline案

1. `font-manifest.json`で候補family、公式URL、version、checksum、licenseを固定
2. `bootstrap --font mplus`等の明示commandだけがnetworkへ出る
3. font binaryはignored cacheへ保存し、checksum不一致なら停止
4. `doctor`が`fc-match`で実際に選ばれるfont fileをreceipt化
5. `build`は固定したFontconfig設定で、OS任せのsilent fallbackを禁止
6. `verify`がPDF内font名と埋め込み／subsetを検査
7. PDFと一緒に使用fontとlicense URLをmachine-readable receiptへ残す

優先順位候補はM PLUS、IPAexGothic、Noto Sans JPとするが、licenseが単純な順という普遍順位ではない。M PLUSまたはNotoを初期fixtureにし、IPAexはIPA Font Licenseに沿うdownload・再配布条件を別adapterとして確認する案が扱いやすい。

### security boundary

- input rootより外のrelative pathとabsolute pathを拒否
- `http:`、`https:`、`file:`等のURLを既定拒否
- raw HTMLは既定無効
- SVGは生成物または検査済みlocal assetだけ許可
- Mermaid／mathはtimeout、入力長、node数を制限
- shell escapeと任意command実行を許可しない
- build processへnetwork権限を与えない
- WeasyPrintにはrestricted URL fetcherを渡す
- memory、CPU、page数、画像pixel数の上限を持つ
- untrusted sourceをroot権限でbuildしない

WeasyPrint公式docsも、untrusted HTML／CSSでlocal file leak、network access、長時間render、高memory、SVG由来のriskがあると説明している。

## 昇格候補／Review Gate

`lib/report_builder/`実装前にHuman Reviewで決める。

1. builder codeのlicense:
   - 現行どおりCC-BY-4.0
   - 新規codeだけApache-2.0としてsubdirectoryで明示
   - repository全体のlicense構造を別変更で再設計
2. 第一PDF engine:
   - WeasyPrint
   - Typst
3. mindmap:
   - Mermaid + headless renderer
   - 最小subsetを別方式でSVG化
4. 初期font:
   - M PLUS
   - Noto Sans JP
   - IPAexGothic
5. generated PDFの保存先と公開review

実装承認の受入条件:

- 一commandでoffline再buildできる
- `venv`、`node_modules`、font binary、browser binaryはGit未追跡
- manifest、lock、checksum、license noticeはGit追跡
- source外pathとnetworkを既定拒否
- 日本語、数式、画像、mindmapを含むfixtureが通る
- font fallback、埋め込み、page数、PDF metadataを機械検査
- 全page PNGをHuman Review
- `git diff --check`とrepo-local testが通る
