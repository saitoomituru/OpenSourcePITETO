## 1. 対象・範囲・除外

### 対象

OpenSourcePITETOを、非技術者へOSS生態系のフリーライド問題と再生産費問題を説明するテストケースとして使えるか検証する。

ここでいう「フリーライド問題」は、ライセンスに従う個々の利用者を泥棒と呼ぶ話ではない。

```text
知識・code・recipeの便益は広く分散する
                     ↓
保守・説明・実験・生活の費用は少数へ集中する
                     ↓
利用可能性と再生産可能性が接続されていない
```

という制度工学上の非対称を対象にする。

### 今回確認すること

- ポテチを食べながらなら、非技術者がOSSの「利用可能」と「維持可能」の違いを説明できるか
- 芋、家庭設備、GitHub Codespaces、Codex等を使った低い参加障壁が、説明実験に有用か
- 構造化workspace、manifest、AGENTS／context規約と自然言語agentがあれば、非プログラマもOSS知財管理・研究開発・運用を体験できるか
- 参加者が自分の別OSS repositoryの資源問題と比較できるか
- 笑える芋ナラティブが、問題を矮小化せず入口を広げられるか
- 「マーケ砲」として強い言葉を作りつつ、未検証claimを事実へ偽装せずに済むか

### 確認しないこと

- 全OSS projectが同じ資源問題を持つという一般化
- GitHub、Microsoft、企業利用者または個人利用者の故意・違法性
- 寄付、法人、スポンサー、課税、公共調達の最終制度設計
- OpenSourcePITETOが既にOSS生態系問題を改善したという成果claim
- CodespacesまたはCodexが物理的に芋を調理するというclaim
- Copilot、Codex等が権利者、法務専門家、公開責任者または人間の同意主体になるというclaim

## 4. テストケースとしての芋

### `[FACT]` 現在確認できること

- このrepositoryには、家庭設備へ移植したポテトチップス工程の日本語READMEと米語意訳がある
- 実食可能だった一回の実機試験と画像が記録されている
- recipeと文書は公開licenseで再利用可能である
- `note/`には、別の芋、器具、失敗、Recoveryを記録する規約とtemplateがある
- GitHub上の文書はCodespaces、ローカルeditor、または対応するagent環境でfork・編集・比較できる

### `[FACT]` 再現できないこと

- CodespacesやCodexだけでは、物理的な芋、油、オーブン、味覚、食感を生成・確認できない
- READMEをforkしただけでは、ポテチの再現にも、OSS再生産問題の改善にもならない
- star、fork、閲覧数だけでは、誰の生活・保守費が支えられたか分からない

## 5. なぜ芋が説明装置になり得るのか

### `[INTERPRETATION]`

codeは、非技術者から見ると保守費が見えにくい。画面上では無限に複製でき、元ファイルも減らないからである。

芋なら、同じ構造が口と台所で見える。

| OSS生態系 | OpenSourcePITETO |
|---|---|
| sourceを取得する | recipeを読む |
| forkする | 自分の台所へ工程を移植する |
| buildする | 芋を切り、揚げ、追い乾燥する |
| testする | 冷却後に食べる |
| bugを見つける | フニャる、焦げる、粉が落ちる |
| issueを書く | 条件と失敗をnoteへ残す |
| maintainer cost | 説明、試作、油、電力、洗い物、身体時間 |
| downstream benefit | 他人が同じ穴へ落ちず、ポテチを食える |

recipeはコピーしても減らない。しかし、recipeを作り、失敗を食らい、写真を整理し、説明し、更新する人間の腹、電力、時間は減る。

この差を一枚のポテチで説明できるなら、芋はOSS制度問題の低コストな翻訳器になり得る。

参加者は、自分が保守・利用・観測できる別OSSを一つ選ぶ。秘密情報や他人の家計を出さず、分かる範囲だけ比較する。

| 問い | OpenSourcePITETO | 比較するOSS |
|---|---|---|
| 誰が直接使うか | recipeを読む／調理する人 |  |
| 便益は何か | 食べられる成果物、失敗回避、知識 |  |
| コピー費は何か | 文書取得は小さい |  |
| 再生産費は何か | 芋、油、電力、器具、身体、記録 |  |
| 見えない保守は何か | 洗い物、安全確認、翻訳、note整理 |  |

### 比較後の質問

1. そのOSSは「無料で取得できる」ため「無料で維持できる」と誤認されていないか。
2. downstreamの売上・業務・研究便益と、upstreamの再生産費は接続されているか。
3. 金銭以外に、review、保守、計算資源、電力、場所、翻訳、法務会計を戻せるか。
4. 支援がroadmap支配、永続support、独占権へ変換されていないか。
5. maintainerが食べて寝て撤退できることは、依存関係の外部扱いになっていないか。

## 7. 自然言語OSS寺子屋としての体験価値

### `[SOURCE POSITION]`

芋は単なる説明用の比喩ではない。

構造化されたworkspace、manifest、局所`AGENTS.md`、note規約、license、Git履歴があり、GitHub Codespaces、Copilot、Codex等の自然言語interfaceから触れられるなら、非プログラマも次を手で体験できる可能性がある。

- 知識を公開する前に、何が事実で何が仮説か分ける
- 誰が作ったか、何を参考にしたか、どこを変えたか残す
- 正本と翻訳、実験noteと標準recipeを分ける
- branchで試し、diffで変更を読み、commitで時点を保存する
- Issueで未解決とSupply不足を共有する
- licenseで再利用可能範囲を示す
- forkと改変を敵対や盗用だけでなく、Provenance付きの派生研究として扱う
- 自分のprojectと他projectの責任境界をmanifestで読む

これは「プログラムを書けるようになる」だけを目的にしない。

```text
自然言語で問いを立てる
    ↓
workspaceで対象範囲を読む
    ↓
manifestでproject間の責任を読む
    ↓
context規約で事実・仮説・非公開を分ける
    ↓
note／Issue／branchへ変更を置く
    ↓
diff、review、commit、forkで知識の系譜を体験する
    ↓
芋を食べ、物理世界で結果を受け取る
```

この一連を、OSSの学術性――再現、反証、出典、派生、失敗保存――と、OSSの精神性――知識を囲わず、他者が続きを掘れる状態で渡すこと――の体験価値として検証する。

ここでいう「精神性／スピリチュアル」は、超自然現象が実証されたという意味ではない。共有、贈与、系譜、撤退自由、他者による再解釈を身体で経験するという文化的・内面的な意味で使う。科学の証拠定規と、参加者の内面experienceを混ぜない。

### 科学とポテト・スピリットの二輪

AIはrecipeを構造化できる。

- 工程を分ける
- 温度、時間、器具、変更差分を表にする
- 写真、commit、review、失敗条件を結び付ける
- 複数回の追試から共通点と反例を整理する
- 「観測した」と「うまいと思った」を別fieldへ置く

しかし、その芋がうまいかは、最後には食べた者の口と主観でしか検証できない。

同じ温度、同じ品種、同じ厚さを再現しても、塩気、香り、歯触り、思い出、空腹、誰と食べたかによって「うまいポテト」は一人ずつ違う。AIはその発言を記録・比較できるが、本人の代わりに味わったことにはできない。

```text
科学／AIの車輪
  ├─ recipe
  ├─ 条件
  ├─ 差分
  ├─ 再現
  ├─ 反例
  └─ review整理

口／自我の車輪
  ├─ うまい
  ├─ 好み
  ├─ 記憶
  ├─ 身体感覚
  ├─ 誰と食べたか
  └─ また食いたいか

             🥔
      二輪が回ってPOTATO DEPLOYED
```

客観記録だけでは、人類が何を大事にしたかったかが抜ける。主観だけでは、他人が同じ芋へ近づく足場が残らない。

だから必要なのは、科学でスピリットを消すことでも、スピリットで科学を上書きすることでもない。

> AIと科学は、うまい芋へ至った道を整備する。
>
> その道の先で「うまい」と言うのは、お前の口だ。
>
> うまいポテトは複製不能な個人体験であり、共有すべき人類の資産でもある。

ここでいう「資産」は独占価格が確定した知財という意味ではない。人類が保存・追試・改良する価値のあるexperienceというPositionである。

### 誰にとってうまいポテトか

「うまい」をlogへ残すには、点数だけでなくObserverを残す必要がある。

```yaml
potato_taste_receipt:
  batch_ref:
  recipe_revision:
  observed_at:
  observer_ref: pseudonymous-or-private
  observer_authority: self-report
  world_or_setting:
  purpose: snack | experiment | meal | social
  body_context:
    hunger: unknown
    fatigue: unknown
    dietary_restriction: private-or-declared
  prior_expectation:
  sample_state:
    temperature:
    cooling_time:
    seasoning:
  observation:
    crispness:
    aroma:
    salt:
    texture:
  subjective_effect:
    delicious_to_me:
    would_eat_again:
    memory_or_association:
  observer_effect:
  agent_role: structure-and-compare-only
  unknown:
  publication_scope:
```

`observer_ref`は、本名公開を要求しない。本人の味覚reportは本人のauthorityで有効だが、全人類の味覚を代表しない。

### ポテトにおけるObserver Effect

ここで扱う観測者効果は、物理量子論の効果を料理へ借用して証明する話ではない。少なくとも三種類を分ける。

1. **破壊的試食**: 一枚食べると、そのsampleは消える
2. **時間介入**: 5分ごとの試食、扉の開閉、取り出しで加熱・冷却条件が変わる
3. **意味介入**: 商品名、期待、空腹、他人の感想、作った苦労が「うまい」の評価へ影響し得る

AIはこれらをfieldへ整理し、別Observerのlogを同一人物の平均値へ潰さず比較できる。しかし、どの評価を採用するか、誰のためのポテトを作るか、別World／別recipe branchへ分けるかは意味管理の課題になる。

## 7. SphereOS Atlantisへの補足動線

PITETO内で完結するのは、一回の調理、Observerの自己申告、recipe差分、写真、note、Issueまでである。

次の規模へ進む場合は、SphereOS Atlantisの意味・次元管理棚へルーティングする。

- 複数Observerの「うまい」を、一つの真理scoreへ潰さず管理する
- 同じ人物でも、時刻、身体、目的、場所が違うlogを別Contextとして保持する
- どのObserver／World／目的に対するrecipeかをFoldする
- agentが整理したlogと、人間が実際に味わったOAEを分ける
- 過去の味覚logを、現在の評価から遡って書き換えない
- 未処理、失敗、拒否、再試験待ちを、次のagentへsource付きで渡す

### 現在の実装境界

2026-07-24時点で参照した公開資料から、次を分ける。

```text
利用可能な足場
  ├─ AGENTS.md／Manifest／sourceを読むPrompt Engineering
  ├─ PLIという自然言語interaction surface
  ├─ MAGI三Position／composite Skill workflow: ALPHA
  ├─ 動的source resolver: LOCAL-READ TESTED
  └─ OAE temporal validator: ALPHA

未実装／資源・review待ち
  ├─ standalone Atlantis runtime
  ├─ FAMLog／OAE persistence
  ├─ 7D Fold runtime
  ├─ provider discovery／queue／dispatch統合runner
  ├─ 常駐daemon／scheduler
  └─ Archangel Hostの確定責務
```

したがって、PITETOから現在使うのは、agentが`AGENTS.md`、Manifest、参照資料をPLI経由で読み、noteとreceiptを構造化する導線までである。意味管理runnerが常時Observer logを回収しているとは表示しない。

### `[HYPOTHESIS]` 天使の積み残し／罪残しtask

これは宗教的な罪をAIが判定する機能ではない。

```text
天使の積み残し
  = 監査Positionが発見したが、資源・authority・証拠不足で完了できないtask

罪残し
  = failure、refusal、timeout、Semantic Stop、未確認を
    成功logで上書きせず、次のrunへ残す比喩
```

将来runnerで自動化するなら、最低でも`source`、`observer`、`position`、`world`、`status`、`stop reason`、`required authority`、`required supply`、`next review`を持たせる。MAGIやArchangelの名前だけで真理、人格、処罰authorityを生成しない。

### `[HYPOTHESIS]` 芋が学術体験に向く理由

- 入力、工程、出力を非プログラマも目視・味覚で確認できる
- recipe、実験差分、写真、失敗、味覚という複数種類の知財を扱える
- 「同じ文書を持つ」と「同じ結果を再現する」の差が明確である
- forkしたrecipeが別の台所条件でどう変わるかを記録できる
- 正解を一つへ固定せず、反例や品種差を研究資産として残せる
- 成果物を食べるため、抽象的なGit操作が生活の循環へ戻る

### 責任境界

Codespacesは作業環境、Copilot／Codex等は補助操縦席である。次は人間または適切なauthorityが判断する。

- 公開してよい情報か
- 自分が権利を持つか、引用・license条件を満たすか
- 食品・熱源・器具を安全に扱えるか
- agentの提案を採用するか
- commit、push、merge、releaseするか
- 他者の知財、人格、生活情報を記録してよいか

自然言語で操作できることと、責任や権利が自動解決することは別である。

## 8. Codespaces／Copilot／Codexで手軽にできる部分

### 文書側の再現

1. repositoryをforkまたは作業branchへ複製する
2. READMEを読む
3. [`TEMPLATE.ja.md`](TEMPLATE.ja.md)からnoteを作る
4. 自分の台所条件または別OSSとの比較を記録する
5. `[FACT]`、`[INTERPRETATION]`、`[HYPOTHESIS]`、`[UNKNOWN]`を分ける
6. pull requestまたはIssue草案として提出する

Copilot、Codex等のagentには、利用できる環境と権限の範囲で次を頼める。

- 既存note・`lib/`を先に探す
- 比較表の空欄や論理の飛躍を指摘する
- 日本語とen-US意訳の主張強度を揃える
- Markdown link、見出し、差分を検証する
- 他project固有情報を勝手に一般化していないか点検する

### 台所側の再現

芋を用意し、READMEの安全境界を読み、人間が調理、観測、試食する。CodespacesとCodexは熱源、手、鼻、舌、消火判断の代わりにならない。

```text
クラウド: 文書、比較、履歴、共同編集
台所:     芋、熱、匂い、食感、安全、洗い物
人間:     両方を閉じるcontroller
```

## 9. `[HYPOTHESIS]` マーケ砲鍛造候補

以下は広告事実ではなく、理解度テストへかけるcandidateである。

- 「OSSは無料でコピーできる。maintainerの晩飯は無料で複製できない。」
- 「forkは一秒。畑と台所と保守は一秒では増えない。」
- 「コードを食って生きられないなら、とりあえず芋食え。」
- 「ポテチを食いながら、誰がOSSの洗い物をしているか考えよう。」
- 「無料で使えることと、無料で育つことは別だ。」
- 「コードを書けなくても、知識のfork、系譜、反証、贈与は体験できる。」
- 「芋から始める、自然言語OSS研究室。」
- 「AIはレシピを読める。うまいかどうかは、お前の口がreviewしろ。」
- 「再現可能なrecipe、複製不能な『うまい』。両方残してOSSだ。」

### 反証・弱体化条件

- 芋の笑いだけが残り、OSSの再生産費を説明できない
- 利用者への罪悪感広告として受け取られる
- 「金を払え」だけへ単純化され、現物、review、保守等のSupplyが消える
- OpenSourcePITETO自身の費用・受益・還流を記録しないまま他projectを批判する
- 非技術者を無知な観客として扱い、比較や改善へ参加させない

## 10. `[HYPOTHESIS]` ナラティブ・ナーチャリング

一発の拡散ではなく、次の理解段階を育てる。

```text
Level 0: 芋を食う
Level 1: recipeを再利用する
Level 2: 失敗と条件をnoteへ返す
Level 3: branch、diff、Provenance、licenseを自然言語で体験する
Level 4: 見えない再生産費を発見する
Level 5: 自分の別OSSと比較する
Level 6: 支配権を買わないSupply routeを試す
Level 7: 他projectでも再現する制度schemaへする
```

評価はPVだけでなく、参加者が次を自分の言葉で説明できるかを見る。

- license上の利用可能性と、生態系の維持可能性は別である
- フリーライド問題は、利用者個人の人格だけでは説明できない
- maintainerの生活と撤退可能性も再生産条件である
- 支援はmerge権、思想支配権、永続保証を自動購入しない
- Codespacesで文書はforkできても、芋と身体はforkできない
- agentは知財・公開・安全の責任主体ではなく、人間の判断を補助する
- 学術的な証拠と、OSS精神を体験したという内面記録は両立するが同一ではない
- AIは味覚主体ではなく、本人の「うまい」を代理検証できない
- 主観reviewを残す価値と、recipeの客観的再現性を分けて説明できる
